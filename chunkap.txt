==================================================
FUTURE DOCUMENT UPDATE / REPROCESSING BEHAVIOR
==================================================

This section describes the already-decided future ingestion behavior.

Do NOT implement this behavior in the current ID sub-phase.

During future ingestion:

1. Loading compares the previous document checksum with the
   newly calculated document checksum.

2. If the document checksum is unchanged:
   - the document is skipped according to the ingestion design.
   - no new Parent/Child chunks are created.
   - no new Parent/Child UUIDs are generated.

3. If the document checksum has changed:
   - the document is reprocessed.
   - the document is re-chunked.
   - all Parent chunks are recreated.
   - all Child chunks are recreated.
   - new Parent UUIDs are generated for the newly created Parents.
   - new Child UUIDs are generated for the newly created Children.
   - the new Child IDs reference the new Parent IDs.
   - new checksums will be generated in the future checksum phase.
   - the complete metadata will be regenerated later.

IMPORTANT:

A checksum difference does NOT directly modify an existing
parent_id or child_id.

Instead:

old chunks are replaced by newly created chunks,
and those newly created chunks receive new UUIDs.

Therefore:

OLD VERSION
Parent A → parent_id = UUID-1
Child A  → child_id = UUID-2
           parent_id = UUID-1

Document changes

NEW VERSION
Parent A' → parent_id = NEW UUID
Child A'  → child_id = NEW UUID
            parent_id = NEW Parent UUID

Do NOT attempt to preserve the old Parent/Child UUIDs across
a full document reprocessing.

Do NOT attempt chunk-level matching.

Do NOT compare old child checksums against new child checksums
to reuse IDs.

Do NOT implement incremental chunk reuse.

The frozen architecture intentionally compares the document
checksum at the document level and reprocesses the entire
document when it changes.
